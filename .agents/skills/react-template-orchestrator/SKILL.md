# React Template Orchestrator

## 언제 사용하는가

- 이 저장소에서 화면, 라우트, 인증·메뉴, 자동 주입 전역, API 호출, 서버 엔드포인트, 환경 변수, 빌드·배포 경로를 변경할 때 사용한다.
- 한 파일의 수정이 barrel, 타입 선언, 접근 로그 키, 프록시 순서 또는 생성 결과에 미치는 영향을 판단할 때 사용한다.
- 설명만 하거나 코드 변경 없이 진단하라는 요청에서는 탐색과 보고까지만 수행한다.

## 필요한 입력

- 사용자의 목표, 허용된 변경 범위와 완료 기준
- 대상 화면·API·서버 동작 또는 실행 환경
- 실제 브라우저·서버 검증 필요 여부와 실행 가능한 외부 서비스
- 현재 `git status --short`와 관련 파일의 기존 변경

정보가 부족해도 안전한 읽기 작업부터 진행한다. 결과를 크게 바꾸는 선택, 운영 명령, 외부 시스템 변경에만 추가 권한이나 사용자 판단을 요청한다.

## 기본 운영 방식

- 기본 패턴은 한 소유자가 분석 → 설계 → 구현 → 검증 → 리뷰를 이어가는 순차 파이프라인이다.
- 별도 작업자는 사용자가 요청했고 읽기 분석·보안 리뷰·서로 다른 화면 검증처럼 경계가 독립적일 때만 사용한다.
- 같은 파일, 같은 `dist`/`build`, 같은 개발 포트나 PM2 프로세스를 공유하는 작업은 병렬 실행하지 않는다.
- 짧고 저위험인 작업은 대화 안에서 인수인계한다. 중단·감사·재개 가능성이 있는 작업만 `_workspace/01_request.md`, `02_design.md`, `04_validation.md`, `05_review.md`를 만든다.

## 작업 흐름

### 1. 상태와 실행 경계 확인

1. 사용자의 요청을 기능, 수정 범위, 검증 기준으로 짧게 정리한다.
2. `git status --short`로 기존 변경을 확인하고 덮어쓰지 않는다.
3. `.nvmrc`, 루트와 대상 패키지의 `package.json`, `.env.example`, 관련 진입점과 barrel을 읽는다.
4. 루트, `client`, `server`가 별도 설치 경계임을 전제로 명령을 선택한다. 의존성을 추가하면 실제 import 주체의 `package.json`에 직접 선언한다.

### 2. 영향 범위 추적

`references/architecture.md`의 변경 영향표를 사용해 최소한 다음 연결을 확인한다.

- 관리자 화면: 구현 → 인접 `index.ts` → 상위 barrel → `router/index.tsx` → `AccessLogger` → 외부 메뉴 URI·접근 키
- 자동 주입 전역: 실제 export → `ProvidePlugin*.js` → 대응 전역 `.d.ts` → ESLint globals → 소비 코드
- API 호출: 요청·응답 타입 → `global/api`/`@pdg/api` 옵션 → Axios XSRF 설정 → 개발·운영 프록시 재작성
- 서버 로컬 경로: 프록시 전 로컬 라우트 → 프록시 → body parser → 배포 훅 → 정적 파일 → SPA fallback
- 환경·운영: `.env.example` → Webpack/Express 소비 코드 → HTTPS·세션·keep-alive·PM2 영향
- 빌드: 클라이언트 `dist`와 분석 보고서 → 서버 `dist/app.js` → EJS 렌더링·PM2 실행 경로

### 3. 구현

1. 저장소의 기존 파일명, export 방식, 타입 분리, 코멘트 형식을 우선 재사용한다.
2. 서로 연결된 계약은 같은 변경에서 갱신한다. 타입 오류를 숨기기 위한 새 `any`, 광범위한 lint 무시 또는 검사 완화는 사용하지 않는다.
3. 자동 주입 식별자를 임의로 로컬 import로 치환하지 않는다. 반대로 새 외부 패키지는 우연한 전이 의존성에 기대지 않고 해당 패키지 경계에 직접 선언한다.
4. 서버에서는 미들웨어와 라우트 순서를 동작의 일부로 취급한다. 외부 API, Redis, Git, PM2 호출은 실패와 재시도 시 부작용을 검토한다.
5. 생성물이나 배포 브랜치를 직접 수정하는 대신 소스와 설정을 수정한다.

### 4. 검증

변경 범위에 맞는 좁은 검사부터 시작해 필요한 게이트까지 넓힌다.

1. 수정 파일의 import/export, 전역 타입, 라우트, 환경 키 참조를 `rg`로 교차 확인한다.
2. 코드 변경은 루트에서 `npm run verify`를 실행한다. 이는 client/server lint와 TypeScript 검사이며 자동 테스트를 포함하지 않는다.
3. Webpack, Babel, 환경 주입, 정적 자산, 서버 번들 또는 배포 경로 변경은 `npm run build`를 추가한다. 생성 디렉터리가 바뀔 수 있음을 먼저 확인한다.
4. UI 변경은 `npm run dev`에서 인증 유무, 메뉴 로딩, 대상 라우트, 로딩·빈 상태·오류·반응형 동작을 직접 확인한다.
5. 서버 또는 프록시 변경은 가능한 경우 `npm run server:dev`와 실제 HTTP 요청으로 로컬 라우트 우선순위, 상태 코드, 본문과 `/api` 재작성을 확인한다.
6. `git diff --check`, 변경 범위 diff, `git status --short`로 종료 상태를 확인한다.

실행할 수 없는 검증은 성공으로 표현하지 말고, 미실행 이유와 남은 위험을 결과에 적는다.

### 5. 리뷰와 전달

- 원 요청 충족, 연결된 계약 누락, 인증·권한, 오류·빈 상태, 운영 부작용과 검증 증거를 자체 리뷰한다.
- 세션, 보안, 배포, 프로세스 제어 또는 데이터 노출 변경은 별도의 위험 기반 리뷰 단계를 둔다.
- 복잡하거나 중단 가능한 작업은 `_workspace/05_review.md`에 `통과`, `수정 필요`, `재검토 필요` 중 하나로 기록한다.
- 최종 보고에는 변경 파일, 핵심 동작, 실행한 검증과 실행하지 못한 검증을 구분한다.

## 실패 정책

- 외부 API, Redis, HTTPS 인증서, Slack, GitHub webhook, PM2가 없어 실패한 검증은 코드 실패와 구분한다.
- 검사 실패를 기존 문제로 판단하려면 변경 전 상태나 관련 없는 파일이라는 증거를 남긴다. 실패를 우회하기 위해 검사를 약화하지 않는다.
- 리뷰가 `수정 필요`이면 한 차례 수정·재검증하고, 같은 문제가 반복되거나 범위 확대가 필요하면 사용자에게 알린다.

## 산출물

- 요청에 맞는 소스·설정 변경
- 필요할 때만 생성하는 `_workspace/01_request.md`, `02_design.md`, `04_validation.md`, `05_review.md`
- 실행한 명령과 결과가 포함된 최종 요약
